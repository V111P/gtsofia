# GT Sofia virtual-board proxy

Render serves a combined arrival API for **surface-transport virtual boards** (trams, buses and trolleybuses). It merges explicit Sofia Traffic GTFS-RT Trip Updates with a compact timetable index generated from the site's current GTFS/OSM data.

## Source priority

- An explicit RT `arrival.time` or `departure.time` for the exact trip and requested stop wins over the static timetable.
- If the RT update is absent for that trip/stop, or its relationship is `NO_DATA`, the active scheduled time is used.
- `SKIPPED`, canceled and deleted trips are not restored from the timetable.
- RT and scheduled rows are merged, sorted by arrival time and returned with `source`, `isRealtime` and `isScheduled` provenance.
- If the RT feed is stale or temporarily unavailable but Render is running, upcoming scheduled arrivals remain available.
- No delay is propagated from another stop and no intermediate time is invented.

## Static timetable index

`data/virtual-board-schedules.json` is generated by `Scripts/transport_data/output.py` from the same GTFS/OSM model used by the Schedules page. It contains surface routes only, OSM-first destination names, per-stop scheduled times and compact active-service date bitsets. The daily GitHub Actions workflow commits this file alongside `data/`. The metro is excluded from this proxy index; it continues to use `data/metro-board.json` in the Vercel API.

## RT validation and cache

- Source: `https://gtfs.sofiatraffic.bg/api/v1/trip-updates`.
- RT Trip Updates are cached for up to 60 seconds and are never served after 120 seconds of source-feed age.
- Static `stops.txt`, `routes.txt` and `trips.txt` metadata resolve stop IDs/public stop codes and enrich RT results. Scheduled times come from the separately generated local index.

## Run locally

Node.js 18 or newer is required. The generated timetable index must exist at `realtime-proxy/data/virtual-board-schedules.json`.

```bash
cd realtime-proxy
npm install
npm start
```

The service listens on `http://localhost:10000` by default (or `PORT`).

## Endpoints

- `GET /health`
- `GET /api/stops/:stopIdOrCode/arrivals?limit=30`

Example: `GET /api/stops/1247/arrivals?limit=1000`. The response exposes `realtimeCount`, `scheduledCount`, `realtimeAvailable`, `feedTimestamp`, `scheduleGeneratedAt`, and an `arrivals` array. Each arrival carries `source: "realtime"` or `source: "schedule"`. The proxy returns all candidates within the six-hour horizon (up to 1000 rows for the virtual-board request); Vercel groups them by route and normalized OSM destination and takes the next three.

## Deploy to Render

The root `render.yaml` configures `realtime-proxy/` as the Root Directory, `npm install` as the build command, `npm start` as the start command and `/health` as the health check. The Vercel project that hosts root-level `api/virtual-board.js` must use the repository root and set `SOFIA_REALTIME_PROXY_URL` to the Render HTTPS origin.
